## 2. Trimmed: the `pth` feature (this session)

`src/weights/mod.rs` read either a packed `ZJM1`/`ZJB1` bundle (what wasm always uses —
`pack-models`'s output) or a raw upstream `.pth` file (a ZIP + a ~450-line data-only pickle
interpreter, `src/weights/{pickle,zip}.rs`), told apart at **runtime** by the file's magic bytes.
Because that branch was runtime, not compile-time, the pickle interpreter was reachable code and
the linker could not drop it even though the wasm build never takes that branch. Fix: split the
two small always-needed types (`DType`, `TensorRef`) into `src/weights/dtype.rs`, and gate
`pickle.rs` + `zip.rs` + the `Backing::Torch` variant + the ZIP branch of `Checkpoint::parse`
behind a new additive `pth` feature (`Cargo.toml`: `default = [..., "pth"]`, `cli = [...,
"pth", ...]`) — on by default (native/CLI users see zero change), off for wasm because
`wasm/Cargo.toml` never lists it. With `pth` off, `Checkpoint::parse` on a non-packed file
returns an error instead of trying to parse pickle.

Verified: `cargo test --lib --tests --all-features` (pth ON, the default) — 13 test binaries,
all pass, including `tests/weights_ref.rs` (`every_upstream_checkpoint_parses`,
`common_int_y_012`, ...) which exercises the ZIP+pickle path directly. `cargo clippy --all-targets
--all-features -- -D warnings` clean. `cargo fmt --check` clean.

**Note on `.debug_*` sections:** an earlier run of `cargo bloat` against the same `--target-dir`
forced a recompile with DWARF debug info on (cargo-bloat needs it and passes its own debug flags,
clobbering the `debug = false` release artifact in place) — that recompile is NOT what ships;
`web/scripts/build-wasm.sh` was re-run clean afterward and the table above and every measurement
below are from that clean rebuild (929,301 / 891,017-byte raw files, no `.debug_*` sections).
**`cargo-bloat --crates` itself never completed**: it refuses non-`bin`/`dylib`/`cdylib`-only
workspaces on this `-Z build-std` + `wasm32-unknown-unknown` + `crate-type = ["cdylib",
"rlib"]` combination ("only 'bin', 'dylib' and 'cdylib' crate types are supported") — a tool
limitation, not something fixable from this repo. `twiggy top`/`dominators` (above and below)
cover the same ground.

`twiggy dominators -d 2` (raw file, so it can resolve names): `decode()`'s retained subtree is
33.26% of the binary (296,380 bytes) — expectedly almost the whole decoder graph, since one
exported function is the only reachable root. No surprise dominator found (no unexpectedly-large
subtree hanging off an unrelated export).

**Conclusion: the requested candidates were already clean.** `zenpixels-convert`/`zencodec`
were never dependencies of this crate to begin with, and `zenpng`/`rayon`/`imgref`/`rgb` were
already behind `cli`/`parallel`, both off for the `simd` wasm build. The one real find was the
pickle interpreter, fixed above.

## 3. Measured and REJECTED: `opt-level = "z"`

Added `[profile.wasm-release-z]` to `Cargo.toml` (inherits `wasm-release`, `opt-level = "z"`) —
kept in the repo as a documented, inert comparison profile, not built by
`build-wasm.sh`.

| | raw | after `wasm-opt -O3` | after `wasm-opt -Oz` | decode (min / median of 8, node, `line-plot` 0.25 bpp stream) |
| --- | ---: | ---: | ---: | ---: |
| `opt-level = 3` (shipped) | 891,017 | 362,789 | 361,710 | **690.1 / 697.2 ms** |
| `opt-level = "z"` | 947,791 | 309,641 | 306,223 | **1651.4 / 1697.0 ms** |

`opt-level = "z"` is 14.6% smaller after `wasm-opt -O3` but **2.4x slower to decode**. Rejected:
decode latency is the entire point of this build, and the size win is small next to the model
bundles themselves (12-28 MB each) that dominate first-load bytes. `wasm-release` stays at
`opt-level = 3`.

## 4. Measured and REJECTED (no change, negligible either way): `wasm-opt -Oz` vs `-O3`

Holding `opt-level = 3`: `-O3` 362,789 bytes vs `-Oz` 361,710 bytes (0.3% smaller) — decode
690.1ms (`-O3`) vs 718.2ms (`-Oz`, within the shared-box measurement noise this session already
documented for wasm-opt in `web/README.md`: "no speed difference resolvable under load"). Kept
`-O3` (current default): the size difference is noise-level and `-O3` is the conservative choice
for a hot path.

## 5. Already in place, verified still correct

- `panic = "abort"` (no unwind tables) — already the `wasm-release` default, unchanged.
- No `std::fmt`/`Debug`-heavy hot loops: the inner NN/entropy kernels
  (`nn::fast::conv::run_row`, `decoder::entropy::decode_component`, etc. — the top of the
  function list above) do not format anything; formatting only appears in `Error` construction
  (`alloc::format!` in `weights/mod.rs`, `decoder/`, etc.), which is unavoidable for useful error
  messages and is not on the decode-success hot path. Not touched.
- Debug names / DWARF: already stripped from the shipped file by `wasm-opt -O3` (confirmed
  above: `web/dist/pkg-simd/zenjpegai_bg.wasm` has zero named items under `twiggy top`, only
  anonymous `code[N]`/`data[N]`).

## 6. Colour policy (unrelated to size, recorded here per the same request)

Canvas output stays 8-bit sRGB RGBA (`wasm/src/lib.rs::decode` truncates any >8-bit source via
`>> shift`); the decoder's `to_rgb_planes` is BT.709/sRGB YCbCr already, so this is colour-correct
for every stream in the demo corpus. HDR / >8-bit canvas presentation is explicitly out of scope
for this browser build — see `web/README.md` "Colour" for the measured P3-canvas-support finding
and where a wide-gamut path would hook in.

## 7. Appended 2026-09-18 (same day, later change): `pkg-webgpu` size cost

Third package variant added by the WebGPU integration (`wasm/` `gpu` feature → `zenjpegai-gpu`,
`wgpu` web backend, `web-sys`, `wasm-bindgen-futures`, `console_error_panic_hook`). Same build
flags/profile as `pkg-simd` plus `--features gpu`; measured by `web/scripts/build-wasm.sh` on
commit `50c97b5` (this workspace, after rebasing onto the E6 encoder work). `pkg-simd`/
`pkg-threads` rebuilt the same run for comparison — the numbers moved from §2 (the encoder
sources and small refactorings since):

| package | after `wasm-bindgen` | after `wasm-opt -O3` | gzip -9 | brotli -q11 |
| --- | ---: | ---: | ---: | ---: |
| `pkg-simd` | 453,501 | 377,496 | 155,837 | 128,817 |
| `pkg-threads` | 753,783 | 502,340 | 187,204 | 150,661 |
| `pkg-webgpu` | 923,401 | 663,094 | 270,652 | 218,045 |

WebGPU synthesis costs **+285,598 bytes optimized (+76%)** over `pkg-simd`, **+114,815 gzip /
+89,228 brotli**. The whole delta is `zenjpegai-gpu` + `wgpu` + `naga`-free shader plumbing
(wgpu's web backend is thin — no WGSL compiler ships; shaders are `createShaderModule` strings).
Justified as an optional package: `worker.js` probes `navigator.gpu.requestAdapter()` first and
only downloads `pkg-webgpu` when a non-software adapter answered (or the pool's `gpu` mode opts
into software adapters for testing), so browsers without usable WebGPU never pay the bytes; both
the size and the extra fetch are opt-in at runtime, not page weight by default.
